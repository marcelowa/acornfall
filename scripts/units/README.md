# Where the unit files went

They are not here any more. The unit and the plist are **generated by `acornfall machine install`** from a
copy embedded in the binary (`gateway/cmd/acornfall/units/`), from the declaration in
`$ROOT/state/machine.json` — the address, the two folders and the symlink it starts. Nobody edits a unit
by hand: a hand edit is undone by the next install, which is also the repair (ADR 0030, amended).

```
acornfall machine install     write the unit, enable it, linger it, verify it answers
acornfall machine uninstall   stop it, remove it and the binary; the mount and the workspaces stay
acornfall machine purge --yes remove the product and the mount; without --yes it removes nothing
```

What is written, for reference:

- Linux: `~/.config/systemd/user/acornfall-machine.service`, starting `~/.acornfall/bin/acornfall machine
  serve` with `--root`, `--home`, `--host` and `--port`. `StartLimitIntervalSec=60`/`StartLimitBurst=3`
  belong to `[Unit]` — systemd reads them there and nowhere else, so in `[Service]` a binary that cannot
  run would restart for ever instead of going to `failed`.
- macOS: `~/Library/LaunchAgents/dev.acornfall.machine.plist`, the same symlink through `sh -c exec`
  because launchd does not expand `~`, and `ThrottleInterval=10` because launchd has no
  `StartLimitBurst` — it only slows a restart loop, and the service's own boot marker is what undoes a
  binary that cannot start.

The symlink path is the contract: it is how the service knows which binary it may replace (ADR 0031).
Started from anywhere else — a package manager's tree, `~/.local/bin` — it supervises and applies the
product's releases, and refuses to update itself, with a line in `is.json` saying why.
